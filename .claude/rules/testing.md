# 测试规则

## 总原则

- 新增核心逻辑时，应优先补充测试
- 修复 bug 时，应优先补充复现该 bug 的测试
- 测试应覆盖关键业务路径、边界条件、错误分支
- 测试要可读、可维护，不要堆砌无意义断言

## 后端测试

### 应重点测试的层
- Service：核心业务逻辑、事务、分支判断、错误语义
- Repo：复杂查询、分页、更新白名单、事务行为
- Converter：字段裁剪、脱敏、转换正确性

### 不建议过度测试的层
- Controller：只测试关键参数绑定、响应状态、统一错误响应
- 简单 getter / setter / 纯样板代码无需机械测试

### 测试要求
- 核心 Service 必须覆盖成功分支与失败分支
- 涉及权限、状态流转、幂等时必须补测试
- 更新接口应验证白名单字段不会误更新敏感字段
- 列表接口应验证分页和筛选逻辑

## 前端测试

### 应重点测试的内容
- composables：状态流转、交互逻辑、边界行为
- stores：状态变更、派生数据、关键行为
- 关键业务组件：输入、输出、条件渲染、事件触发

### 测试要求
- 重要页面行为应覆盖核心交互路径
- 表单提交流程应覆盖校验失败、请求成功、请求失败
- 关键权限展示逻辑应覆盖可见与不可见两种情况

## 测试风格

- 测试名称要体现业务语义
- 一个测试只验证一类核心行为
- 避免过度依赖实现细节
- 优先从输入和输出验证行为

## 禁止事项

- 修 bug 不补测试
- 只测 happy path，不测异常分支
- 测试名称含糊不清
- 断言与业务行为无关
- 为了通过测试而写脆弱实现
